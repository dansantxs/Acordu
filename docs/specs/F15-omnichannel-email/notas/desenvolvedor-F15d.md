# Notas do desenvolvedor — F15d (etapa 4)

Premissas técnicas do PR da rota de entrada por e-mail (F15-05, F15-19, F15-22, F15-89; design D1, D5, D6, D12 e D14; ADR 0016, itens 1 a 3 e 8). Sessão sem SDK .NET: o backend foi lido com cuidado, mas só compila e roda na CI. O Worker foi instalado, tipado, testado e empacotado aqui (`pnpm typecheck`, `pnpm test`, `wrangler deploy --dry-run`).

## API

- **Rota** `POST /internal/email/entrada` (`Api/EntradaEmail/EntradaEmailEndpoints`), fora do OpenAPI (`ExcludeFromDescription`, como os jobs; `openapi/*.json` e os tipos do front não mudam). Token em `X-Email-Token` contra `EmailEntrada__Token`, em tempo constante; sem o token configurado, `404` para tudo. Depois: `Content-Length` acima de `EmailEntrada__TamanhoMaximoBytes` → `413` antes de ler; o `IHttpMaxRequestBodySizeFeature` (quando existe) fica no mesmo limite; o resto vai ao `RecebedorDeEmail`. `202` sem corpo para todos os desfechos, menos `GrandeDemais` (`413`).
- **Ordem** (D12): token → tamanho declarado → destino → empresa → leitura do MIME (tamanho real) → registro. Premissa: com o corpo em partes (sem `Content-Length`), um e-mail grande demais para uma empresa desconhecida, desligada ou só leitura recebe `202` sem o corpo ser lido (nada é gravado do mesmo jeito, e o Worker já recusa antes pelo `rawSize`). Ler 25 MiB só para responder `413` a quem seria descartado gastaria CPU do Cloud Run à toa.
- **Folga do limite:** o design fala em "limitar o corpo da rota ao mesmo valor, com folga para os cabeçalhos". O corpo da rota é o MIME inteiro, o mesmo que o Worker mede em `rawSize` (os cabeçalhos HTTP não contam no limite do corpo), então usei o mesmo valor nas duas pontas, inclusivo (`rawSize > máximo` recusa; igual passa).
- **Destino → empresa:** `DestinoDeEntrada.Ler` (Application, só formato: domínio igual ao configurado, código no formato do `CodigoDeEntrada`, token depois do "+" guardado como veio para o F15i) e `IEmpresasDeEntrada` implementada em `Persistence.EntradaEmail.EmpresasDeEntrada` (ponto revisado: `IgnoreQueryFilters` só do filtro de tenant, `AsNoTracking`, projeção em Id, só leitura e opção). Teste de arquitetura novo (`EntradaEmailTests` em `Acordu.ArchitectureTests`) falha se outro método da Infrastructure ignorar os filtros e ler `Tenant.CodigoEntrada` numa árvore de expressão.
- **Escopo da empresa:** como o `ExecutorPorTenant`, o `RecebedorDeEmail` (Infrastructure, singleton registrado na `ComposicaoApi` porque depende do `OpcoesEmailEntrada`) abre um escopo para a consulta e outro com `ContextoTenant.DefinirEquipe(tenant)` para o `ComandosEntradaEmail` (Application, registrado em `CasosDeUso`). A guarda de só leitura vale de novo na gravação: se a empresa ficou só leitura entre a consulta e o commit, a `EmpresaSomenteLeituraException` vira o desfecho `SomenteLeitura` (nada gravado).
- **Registro de entrada** (`EmailRecebido`, D6): só os campos que este PR usa (`ChaveEntrada`, `RemetenteHash`, `RecebidoEm`, `Resultado`). Os ids do que o e-mail criou (`SolicitacaoId`, `InteracaoId`, `ItemTriagemId`) e os anexos recusados entram nos PRs que os criam (F15f, F15g, F15h, F15i), com migration aditiva; adiantar colunas que nada preenche deixaria o modelo dizendo mais do que faz. O enum `ResultadoEntradaEmail` já vem com os cinco valores do D6 (texto, sem migration de dados depois).
- **Chave de idempotência** (`ChaveDeEntrada.Calcular`): SHA-256 hex de `"message-id:" + id` ou `"conteudo:" + hash do MIME`, mais `"\n" + destino em minúsculas`. O `Message-ID` é normalizado só tirando espaços e `<>` (o resto é comparado como veio: o local do id diferencia maiúsculas). O prefixo evita que um `Message-ID` igual a um hash de conteúdo colida com a chave por conteúdo. O destino inteiro (com o "+token") entra na chave: o mesmo e-mail à empresa e a uma conversa dela conta nas duas, como o D6 pede para duas empresas.
- **Hash do remetente:** SHA-256 do `From` normalizado por `Common.Email.Normalizar` (o dos contatos), só quando o `From` tem exatamente um endereço válido; senão nulo. A base dos limites por remetente (F15n).
- **Corrida de duas entregas iguais:** a segunda esbarra no índice único `ix_emails_recebidos_tenant_id_chave_entrada` (nome fixo na configuração); o `RecebedorDeEmail` reconhece pelo nome (`EmailsRecebidos.ChaveRepetida`) e responde `202` como repetição, sem `5xx`.
- **Até o F15f**, todo e-mail aceito é só registrado como `IGNORADO` (design §3, "entre um PR e outro"); nada visível é criado e nada é respondido.
- **Leitura do MIME:** pacote `MimeKit.Core` 5.0.0 (a parte de MIME do MimeKit 5; o pacote `MimeKit` 5 virou meta-pacote com a criptografia e o BouncyCastle, que este PR não usa). MIT, sem dependências no net10. Se o D11 (b) entrar (DKIM na API), acrescenta-se o `MimeKit.Cryptography`. O corpo passa por `CorpoLimitado` (conta os bytes, lança `CorpoGrandeDemaisException` acima do limite, calcula o SHA-256 do que passou); depois do parser, o resto do stream é drenado para o tamanho e o hash cobrirem o corpo inteiro. MIME ilegível (`FormatException`, inclusive corpo vazio) → `Malformada`, `202` (menor 6 do `plano-2.md`: a rota não pode responder `5xx` para o servidor de origem não repetir por dias).
- **Log** (F15-109 é do F15n, mas a regra vale desde já, convenções §5): uma linha `Entrada por e-mail: {Desfecho}.` (Information, EventId 410) por e-mail, só com o desfecho. O `413` que o Kestrel lançar na leitura (quando ele impõe o limite antes do `CorpoLimitado`) sai sem essa linha; raro e sem efeito.
- **Classificações:** `EmailRecebido` é da empresa no só leitura e dado no expurgo do cadastro (D6). Por isso entrou também em `DadosDeExemplo.TiposConferidos` e na consulta da situação dos exemplos: um e-mail recebido conta como dado próprio da empresa (a oferta dos exemplos some, como some com qualquer dado). Some no contexto de contato (filtro de cliente como o do `Cronometro`).
- **`EmailEntrada__TamanhoMaximoBytes`** entrou em `OpcoesEmailEntrada` (de 1 byte a 25 MiB; ausente → 25 MiB; inválido impede a subida). `EmailEntrada__DiasRegistro` fica para o F15e, com o passo `expurgo-email-entrada`.
- **Migration:** pedida ao bot por `.github/migration-request` (`EmailsRecebidos`). Deve gerar a tabela `emails_recebidos` (`chave_entrada character(64)`, `remetente_hash character(64)` anulável, `recebido_em timestamptz`, `resultado character varying(40)`, `xmin`) e o índice único `ix_emails_recebidos_tenant_id_chave_entrada`. Sem preenchimento de dados nem linha à mão no `Up`.

## Worker (`infra/cloudflare/email-entrada`)

- Mesma estrutura, versões e lockfile da vigia (o `pnpm-lock.yaml` é o dela: mesmas dependências), `compatibility_date` e `global_fetch_strictly_public` iguais. `DESTINO` e `TAMANHO_MAXIMO` no `[vars]` do `wrangler.toml`; `TOKEN_ENTRADA` como segredo, pelo `deploy.yml`.
- **Corpo:** `message.raw` direto no `fetch`, em stream (sem `Content-Length`; a API conta os bytes). Não usei `FixedLengthStream` para não depender de uma classe que só existe no runtime da Cloudflare (os testes rodam no Node).
- **Respostas:** `2xx` entregue; `413` → `setReject`; qualquer outra (inclusive `404` de token errado) ou falha de rede → lança erro (falha temporária, o servidor de origem repete). Premissa: o `404` também é temporário, para um token trocado só de um lado não perder e-mails; o servidor de origem desiste sozinho depois de alguns dias.
- **Sem `TOKEN_ENTRADA`:** lança erro sem chamar a API (falha temporária), pelo mesmo motivo.
- **Veredito (D11):** o carimbo é a primeira instância de `Authentication-Results` (senão `ARC-Authentication-Results`) cujo servidor é `mx.cloudflare.net` (configurável em `SERVIDOR_AUTENTICACAO`); instâncias de outro servidor são ignoradas. **Conferir no provisionamento** (setup-infra, Parte D, passo 5): o nome do servidor que o Email Routing usa no carimbo, se ele vem no `message.headers` e se o Email Routing tira os `Authentication-Results` com o nome dele que o remetente forjar (se não tirar, vale a primeira instância, que é a acrescentada por último pelo provedor). O alinhamento do DKIM ao `From` é o relaxado aproximado (o mesmo domínio ou um subdomínio do outro), sem a lista de sufixos públicos. `X-Email-Filtro` vai sempre `ok` (o plano gratuito não expõe nota de spam nem antivírus; risco já aceito no G2). A API só usa os dois a partir do F15e/F15f.
- Endereço de envelope fora do ASCII (SMTPUTF8) vira `?` no cabeçalho do pedido, que só aceita texto de um byte; o destinatário válido é sempre ASCII.
- **Log do Worker:** só o resultado, se veio o carimbo e o veredito; nunca endereço, assunto ou conteúdo (teste).
